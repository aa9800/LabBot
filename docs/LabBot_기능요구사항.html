01 데이터 모델

Supabase(Postgres) 테이블 8개. SQL은 labbot_schema.sql에 그대로 있음(붙여넣기만 하면 됨).

테이블핵심 필드비고
profilesid, name, rolerole: user | admin
itemsid, name, category, location, qr_code, total_qty, available_qty, statusstatus: 정상|고장|폐기
loansid, user_id, item_id, borrowed_at, due_at, returned_at, statusstatus: 대여중|반납완료
audit_sessionsid, performed_by, started_at, finished_at, scanned_count
audit_mismatchesid, session_id, item_id, note
safety_eventsid, rule_id, severity, status, source, note, detected_at, assignee_id, due_at, resolution_note, resolved_at
action_logsid, event_id, actor, action, note, created_atsafety_events 감사이력
damage_reportsid, item_id, reported_by, photo_url, ai_result, created_at

02 인증

  • Supabase Auth(이메일/비밀번호)로 로그인·회원가입 처리 — 비밀번호를 직접 저장/비교하지 않음
  • 가입 시 profiles 행 자동 생성, role='user'로 시작
  • 관리자 권한은 클라이언트 코드가 아니라 RLS(Row Level Security)로 DB에서 강제

03 물품 관리

기능조건 / 규칙
등록name, category, location, total_qty 입력 → qr_code는 서버에서 랜덤 발급, available_qty = total_qty로 시작
검색이름 부분일치 + category/location 필터 (동시 적용, AND)
재고 수정available_qty ≤ total_qty 항상 유지
삭제해당 물품에 loans 기록이 있으면 삭제 금지(이력 보존)

04 대여 · 반납

지금 재고 숫자만 +1/-1 하는 방식은 "누가 언제까지 빌렸는지"가 안 남아서 아래 방식으로 교체 필요.

동작조건결과
대여available_qty > 0loans 행 생성(반납예정=오늘+7일 기본), available_qty -1
반납대여중 상태returned_at 기록, status=반납완료, available_qty +1
연체 표시미반납 & 오늘 > due_at저장하지 않고 조회 시점에 매번 계산(파생값)
내 대여 목록로그인 사용자본인 loans만 필터

05 재고 실사

  1. 관리자가 실제로 확인한 item_id 목록을 제출 → audit_sessions 1건 생성
  2. 전체 물품 중 목록에 없는 item은 전부 audit_mismatches에 자동 기록 (note: "실사 시 미확인")
  3. 이 목록은 사람이 체크리스트로 만들 수도, 나중에 로봇이 스캔한 결과로 만들 수도 있음 — 로직은 동일

06 Safety 이벤트

로봇(또는 사람)이 이상을 감지하면 항상 NEEDS_REVIEW로 시작 — 자동 확정 금지.

상태의미
NEEDS_REVIEW방금 감지됨, 검토 전
OPEN오탐 아님 확인
ASSIGNED담당자 지정됨
IN_PROGRESS조치 중
RESOLVED해결 근거 등록됨
CLOSED최종 종결
FALSE_POSITIVE오탐으로 종결

모든 상태 변경은 action_logs에 남긴다(누가·언제·무엇을).

07 파손 신고

  • 사진 업로드(Supabase Storage) + item_id 연결해 damage_reports 생성
  • ai_result는 비워둔 채로 시작 가능 — 사람이 사진 보고 판단해도 됨
  • Gemini 연동 시: 사진을 분석해 ai_result에 텍스트 저장, 최종 판단은 항상 사람이 함

08 챗봇 (실험 물품 추천)

단순 Q&A가 아니라 실험 설명 → 필요 물품 추천 → 장바구니 → 일괄 대여까지 이어지는 기능.

  1. 사용자가 하려는 실험/작업을 자연어로 입력 (예: "LED 회로 실험하려는데 뭐 필요해?")
  2. Gemini가 입력을 해석해 필요한 물품 카테고리/키워드를 추론
  3. 그 키워드로 실제 items 테이블을 검색 — Gemini가 지어낸 물품이 아니라 실재 재고 중에서만 추천
  4. 사용자가 추천 목록에서 원하는 항목을 선택 → 장바구니에 담기 (서버에 저장할 필요 없는 임시 상태)
  5. "일괄 대여 신청" → 선택된 물품들에 대해 loans를 한 번에 여러 건 생성 (4장의 대여 로직을 항목별로 반복 적용)
규칙내용
추천 범위DB에 실제 존재하고 available_qty > 0인 물품만 추천
재고 없는 경우추천에는 표시하되 "재고 없음"으로 별도 표시, 장바구니 담기 비활성화
재고 확정Gemini는 추천만 하고, 실제 대여 가능 여부/재고 차감은 항상 서버(DB) 기준으로 판단

09 로봇 연동 참고 (지금 안 만들어도 됨)
