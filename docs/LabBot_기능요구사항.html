HANDOFF LabKeeper → LabBot

LabBot 기능 명세

화면 디자인은 LabBot 그대로 간다. 이 문서는 LabKeeper에서 실제로 만들고 테스트까지 끝낸 데이터 구조·로직을 Supabase 기준으로 옮겨적은 것 — 지훈님이 그대로 구현하면 되는 요구사항이다.

대상 저장소github.com/9897-prog/LabBot
대상 스택Supabase (Postgres + Auth + Storage)
근거LabKeeper(FastAPI) 프로토타입에서 검증됨
01 이 문서의 목적

디자인은 유지, 로직은 이걸로

LabBot의 화면(홈/물품목록/로그인/관리자/챗봇/mobile-status)과 비주얼은 그대로 쓴다. 지금 진행이 막힌 이유는 기능 방향성이 아직 코드로 안 내려왔기 때문인데, 그 방향성을 LabKeeper에서 이미 만들어보고 실제로 동작 확인까지 끝냈다. 이 문서는 그 검증된 로직을 그대로 옮겨적은 것이다 — 처음부터 다시 고민할 필요 없다.

왜 Supabase 기준으로 썼나 LabBot의 JS 코드에 이미 "Supabase 연동 예정" TODO가 있다. Postgres 기반이라 아래 테이블 설계를 거의 그대로 SQL로 옮길 수 있다.
02 데이터 모델

Supabase 테이블

사용자 인증은 Supabase Auth(auth.users)를 쓰고, 역할(관리자 여부)은 별도 profiles 테이블에 둔다 — 지금 LabBot처럼 JS 안에 관리자 계정을 하드코딩하지 않는다.

테이블핵심 필드비고
profilesid(=auth.users.id), name, rolerole: user | admin
itemsid, name, category, location, qr_code, total_qty, available_qty, statusqr_code는 지금 LabBot에 없음 — 신규 필드
loansid, user_id, item_id, borrowed_at, due_at, returned_at, statusstatus: 대여중 | 반납완료. 지금 LabBot의 "재고 -1/+1 토글"을 대체
audit_sessionsid, performed_by, started_at, finished_at, scanned_count신규
audit_mismatchesid, session_id, item_id, note신규
safety_eventsid, rule_id, severity, status, source, note, detected_at, assignee_id, due_at, resolution_note, resolved_at신규
action_logsid, event_id, actor, action, note, created_atsafety_events의 감사이력
damage_reportsid, item_id, reported_by, photo_url, ai_result, created_atLabBot admin.html에 이미 있는 탭, 테이블만 신규

loans가 핵심이다 — 지금 LabBot은 "누가 빌렸는지" 기록이 전혀 없이 재고 숫자만 바꾸는데, 이러면 연체 추적도, "내가 빌린 물품"도, 실사 대조도 안 된다. LabKeeper에서 이 구조로 대여·반납·연체계산까지 실제로 동작 확인했다.

03 인증 (지금 상태로 두면 안 됨)

지금 상태의 문제

보안 문제 — 지금 코드 상태 js/auth.js가 비밀번호를 평문으로 localStorage에 저장하고, 관리자 계정(admin@labbot.local / admin1234)이 JS 코드에 그대로 노출돼 있다. 개발자도구만 열어도 보인다.
  • 로그인/회원가입 → Supabase Auth의 이메일/비밀번호 로그인으로 교체 (비밀번호를 직접 다루지 않음)
  • 회원가입 시 profiles 행을 하나 만들고 role='user'로 시작
  • 관리자 권한 확인은 클라이언트 코드가 아니라 Supabase RLS(Row Level Security) 정책으로 서버 쪽에서 강제 — "관리자만 items를 수정할 수 있다" 같은 규칙을 DB 레벨에 건다
04 물품 목록 / 홈

지금 화면 유지 + 필드 추가

화면 구성(검색, 카테고리 칩, 재고 배지)은 그대로 두고 데이터만 items 테이블 기준으로 바꾼다.

  • 물품마다 qr_code 발급(랜덤 문자열) — 나중에 실사/로봇 연동에 필요. 지금 화면에 QR 이미지를 안 보여줘도 되지만 필드는 지금 추가해야 나중에 마이그레이션이 안 생긴다.
  • "대여하기" 클릭 → loans 행 생성(반납예정일 = 오늘+7일 등 기본값) + items.available_qty -= 1
  • "반납하기" → 해당 loans 행의 returned_at 기록, status 변경, available_qty += 1

06 실사 (신규 — 재고 정확도 확인)

체크리스트 → 자동 불일치 판정

관리자가 실사 화면에서 물품 목록을 체크하고 제출하면, 체크 안 된 물품은 자동으로 "실사 시 미확인" 불일치가 된다. LabKeeper에서 실제로 이 방식으로 검증했다(제거한 물품이 정확히 불일치로 잡힘).

  1. audit_sessions 행 생성 (performed_by, 시작시각)
  2. 체크된 item_id 목록을 받아 scanned_count에 기록
  3. 전체 items 중 체크 안 된 것마다 audit_mismatches 행 생성

지금은 사람이 체크리스트로 하지만, 나중에 로봇이 스캔한 물품 id 목록을 그대로 이 로직에 넘기면 자동 실사로 바로 이어진다 (11장 참고).

07 Safety 이벤트 (신규 — 로봇 연동 대비)

감지 → 검토 → 조치 → 종결

로봇(또는 사람)이 이상(장애물, 파손 등)을 보고하면 항상 NEEDS_REVIEW로 시작한다 — AI/센서 판정은 오탐 가능성이 있어서 자동 확정하지 않는다.

상태의미
NEEDS_REVIEW방금 감지됨, 사람 확인 전
OPEN오탐 아님 확인됨
ASSIGNED담당자 지정됨
IN_PROGRESS조치 중
RESOLVED해결 근거 등록됨
CLOSED최종 종결 (되돌릴 수 없음)
FALSE_POSITIVE오탐으로 종결

지금 당장 화면이 필요한 건 아니고, 테이블과 로직만 먼저 있으면 나중에 로봇이 붙을 때 화면만 추가하면 된다.

08 파손 신고 + AI 분석

LabBot에 이미 있던 아이디어 — 살리기

admin.html의 "파손 신고 목록" 탭이 이미 있다. 이건 LabKeeper에는 없는 좋은 아이디어라 그대로 발전시킨다.

  1. 사용자가 반납 시(또는 별도 화면에서) 사진 첨부 + "파손 신고" → 사진은 Supabase Storage에 업로드, damage_reports에 photo_url 저장
  2. ai_result는 처음엔 비워두고 관리자가 사진 보고 직접 판단해도 됨 (Gemini 연동은 이후 단계)
  3. Gemini 연동 시: 사진 URL을 Gemini Vision에 넘겨 "파손 여부/정도" 텍스트를 받아 ai_result에 저장 — 최종 판단은 항상 사람이 하고 AI 결과는 참고용으로 표시(Safety 이벤트와 같은 원칙: AI 판정은 확정이 아니라 참고)
09 챗봇

범위를 좁혀서 먼저 동작하게

"이용규칙이 궁금하거나 어떤 실험에 어떤 물품이 필요한지"라는 지금 문구 그대로, 처음엔 고정 규칙 기반 응답으로 시작하는 걸 추천한다 (예: 물품 이름이 메시지에 포함되면 items에서 검색해 위치·재고를 알려주기). Gemini API 완전 연동은 이후 단계로 미뤄도 챗봇 화면 자체는 지금 동작하게 만들 수 있다.

10 mobile-status.html

"로봇을 따라가세요" — 안내(에스코트) 화면으로 구체화

지금은 정적 문구뿐인데, 이 화면의 의도를 "사용자가 찾는 물품이 있는 곳까지 로봇이 안내한다"는 기능으로 구체화하는 걸 제안한다:

  1. 사용자가 items.html에서 특정 물품에 "위치 안내 요청"
  2. 로봇에게 그 물품의 location으로 이동 명령 (11장 API)
  3. mobile-status.html이 로봇의 현재 상태(이동중/도착함)를 짧은 주기로 조회해서 "로봇을 따라가세요" → "도착했습니다, 선반 A-1"으로 문구를 바꿈

로봇이 도착 전까지는 이 화면은 그냥 정적 안내만 유지해도 되고, 실물 로봇이 붙을 때 이 흐름을 채우면 된다.

11 로봇 연동 API (나중을 위한 참고)

지금 안 만들어도 됨 — 형태만 미리 알아두기

LabKeeper의 robot-sim이 실제로 호출해서 검증한 API 형태다. Supabase면 REST(PostgREST 자동생성) 또는 Edge Function으로 거의 그대로 옮길 수 있다. 지금 단계에서 구현할 필요는 없고, 나중에 로봇이 붙을 때 이 모양으로 맞추면 웹 쪽 수정이 최소화된다는 것만 참고.

메서드경로용도
GET/items로봇이 위치별 물품 목록을 가져와 순찰 지도를 구성
POST/audit-sessions로봇이 스캔한 물품 id 목록을 실사 결과로 제출
POST/safety-events로봇이 이상 감지 시 이벤트 생성 (항상 NEEDS_REVIEW)
