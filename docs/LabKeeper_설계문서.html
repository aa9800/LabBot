LabKeeper

실습실·랩 물품의 대여와 재고를 관리하는 웹 서비스. 가상 연구실(디지털 트윈)에서 대규모로 개발·검증한 로직을 실제 Raspbot과 아두이노 게이트로 이식해 현실에서 확인한다.

대상학과 실습실 / 메이커스페이스 / 랩
핵심대여·반납 워크플로우 + 재고관리
확장Raspberry Pi 5 (Raspbot) + Arduino 게이트
개발 형태1인 홈 개발
01 개요 & 목표

웹이 먼저, 로봇은 확장

실습실이나 랩에서는 "이 부품이 지금 어디 있는지, 누가 빌려갔는지, 반납이 늦었는지"를 확인하는 일이 항상 번거롭다. LabKeeper는 이 문제를 푸는 독립적으로 완결된 관리 웹 서비스다. 로봇이나 아두이노가 없어도 등록·검색·대여·실사·통계 기능만으로 실사용 가치가 있어야 한다는 원칙을 그대로 따른다.

Raspbot과 아두이노는 이 웹의 실제 데이터를 갱신하는 물리적 대행자 역할을 한다. Raspbot은 라인트래킹으로 선반 사이를 돌며 QR을 스캔해 재고를 실사하고, 아두이노는 대여소 게이트에서 RFID로 대여·반납을 실물로 확인한다. 둘 다 웹의 대여/재고 레코드를 직접 갱신하며, 단순 조종 인터페이스로 끝나지 않는다.

Design Principle 웹 = 업무의 진실 원천(source of truth). 로봇/아두이노 = 그 진실을 자동으로 확인·갱신하는 센서·액추에이터. 로봇이 멈춰도 웹은 수동 입력으로 100% 동작해야 한다.

세 개의 층

실제 랩 공간을 대규모로 확보하기 어렵기 때문에, 개발·검증은 소프트웨어 상의 가상 연구실에서 진행하고, 실제 하드웨어는 그 결과를 현실에서 확인하는 축소 검증대로 쓴다.

Layer 1
웹 서비스

메인 서비스. 대여·재고·통계의 진실 원천. 로봇 유무와 무관하게 항상 동작

Layer 2
가상 연구실

대규모 실습실을 소프트웨어로 재현한 테스트베드. 여러 대의 가상 로봇으로 개발·반복 검증

Layer 3
실제 Raspbot

소규모 실측 환경에서 물리 동작(현실의 조명·마찰·오차)을 최종 검증하는 Physical AI 증명

02 시스템 아키텍처

세 개의 축

웹 서버가 유일한 진실 원천이며, Raspbot과 Arduino는 각자의 방식으로 REST API를 호출하는 클라이언트로 취급한다.

로봇 클라이언트는 한 벌의 코드로 작성하고, HAL(하드웨어 추상화 계층)만 교체해 가상 로봇과 실제 Raspbot 양쪽에 동일하게 붙인다. 웹 API 입장에서는 호출자가 시뮬레이션인지 실물인지 구분하지 않는다. 아두이노 자체에는 Wi-Fi가 없으므로(SZH-EK013은 우노 호환보드) USB 시리얼로 라즈베리파이나 상시 켜진 PC에 연결하고, 그 브리지가 웹 API를 호출하는 구조를 권장한다.

03 디지털 트윈 & 가상 연구실

같은 코드, 다른 몸

실제 랩 공간과 다수의 실물 로봇을 확보할 수 없으므로, 개발과 반복 검증은 소프트웨어로 만든 가상 연구실에서 진행한다. 핵심은 인식·판단 로직과 센서·구동 인터페이스를 분리하는 것이다 — 로직은 그대로 두고 아래쪽(HAL)만 시뮬레이션/실물로 바꿔 끼운다.

모듈역할비고
perception.pyQR/얼굴 인식 (OpenCV)가상·실물 공통, 수정 없음
controller.py라인트래킹 판단, 정지·스캔·회피 로직가상·실물 공통, 수정 없음
hal/sim_hal.pySim Engine에 HTTP로 카메라 프레임·센서값 요청, 이동 명령 전송가상환경 전용
hal/real_hal.pyPi 카메라·GPIO(초음파/라인센서)·모터 PWM 직접 제어실물 전용

가상 로봇이 제공하는 센서 인터페이스

실제 Raspbot의 클라이언트가 읽는 값과 동일한 모양으로 가상 로봇도 값을 내려준다.

엔드포인트반환값실물 대응
GET /sim/{id}/camera_frame합성 카메라 이미지(PNG) — 거리·각도에 따라 QR 크기/회전/블러 반영Pi 카메라
GET /sim/{id}/ultrasonic레이캐스팅 거리값(노이즈 포함)초음파 센서
GET /sim/{id}/line_sensor4채널 라인 감지 값4채널 라인트래킹 센서
POST /sim/{id}/move이동 명령 반영, 다음 tick 위치 갱신모터 PWM

카메라 프레임은 단순히 "QR이 근처에 있다/없다"로 뭉개지 않고, 실제 pyzbar/OpenCV 디코더가 성공하거나 실패할 수 있는 합성 이미지를 렌더링한다 — 그래야 인식 파이프라인이 시뮬레이션 단계에서 진짜로 검증된다. 1차 거친 스캔(객체 인식)용으로는 구역 안 물건 개수·형태를 단순 도형으로 렌더링해 "몇 개가 감지되는가"까지 함께 검증한다.

가상 지도 = 또 하나의 핵심 기능

관리자가 선반·QR 태그 위치·라인트랙 경로·장애물을 직접 배치해 새로운 지점(랩 지점/브랜치)의 가상 실습실을 등록·관리할 수 있게 한다. 이건 부가기능이 아니라 웹의 정식 CRUD 기능이며, 동시에 여러 대의 가상 로봇을 굴려 대규모 환경을 저비용으로 재현하는 수단이 된다.

Robot Fleet DB에 robots 테이블(id, type: simulated|physical, map_id, status, last_seen)을 두고, 관제 화면 하나에서 가상 로봇 여러 대와 실제 Raspbot 1대를 함께 모니터링한다.

개발 → 실증 파이프라인

  1. 가상 연구실에서 라인트래킹·정지판정·QR스캔·실사 로직을 반복 개발·검증 (sim_hal.py 사용)
  2. 같은 perception.py/controller.py를 그대로 두고 real_hal.py로 교체
  3. 실제 Raspbot + 소규모 실측 목업(책장 1~2단)에서 조명·마찰·인식 오차 등 현실 변수만 최종 검증
  4. 실측에서 드러난 보정치(정지 거리, 인식 임계값 등)를 로직에 반영하고 가상환경에도 동기화

08 라즈봇 연동

2단계 인식: 거칠게 훑고, 필요할 때만 정밀 확인

Raspbot은 물건을 들거나 나르지 않는다(그리퍼 없음). 대신 이동 + 카메라 인식만으로 재고 확인이라는 실제 업무를 수행한다. 객체인식은 개체 단위 식별이 안 되므로(같은 종류 물건을 구별 못함), 순찰의 두 단계에 역할을 나눠 맡긴다.

왜 나누나 모든 선반마다 QR을 정밀하게 읽으려면 로봇이 매번 정확히 정차해야 해서 순찰이 느리다. 반대로 객체인식만 쓰면 "정확히 어떤 물건이 없어졌는지"는 알 수 없다. 그래서 1차는 빠른 객체인식으로 이상 구역만 걸러내고, 2차는 그 구역에서만 QR로 정밀 확인한다.
단계인식 방식하는 일속도/정밀도
1차 · 거친 순찰객체 인식구역별 예상 카테고리·개수와 실제 감지된 개수를 비교, 이상 구역만 표시빠름 / 카테고리 단위
2차 · 정밀 확인QR 인식이상 표시된 구역에만 접근해 QR을 하나씩 읽어 정확히 무엇이 빠졌는지 확정느림 / 개체 단위

단계별 로직

  1. 라인트래킹 센서로 지정 경로(선반 통로)를 따라 이동하며 각 구역에서 객체 인식 실행
  2. 구역별 예상 재고(카테고리/개수)와 감지 결과를 대조 → 맞으면 통과, 다르면 "정밀확인 필요" 표시
  3. 정밀확인이 필요한 구역에만 다시 접근해 정지 후 QR 태그를 하나씩 스캔해 정확한 개체를 특정
  4. 초음파로 통로 장애물 감지 시 정지, 웹에 "일시정지" 상태 표시
  5. (옵션) 얼굴 인식으로 무인시간대 사람 감지를 실사 로그에 병기
  6. 순찰 종료 후 실사 세션 레코드 생성 → 통계 페이지의 재고 정확도 추이에 반영
IMU(MPU6050) 추가 Pi 5의 I2C 핀에 MPU6050을 추가하면, 모터 명령만으로 추정하던 헤딩(dead-reckoning)을 실제 측정값으로 보정할 수 있다. 바퀴 미끄러짐 때문에 생기는 라인트래킹 오차가 줄고, 급격한 기울임·충격을 감지해 "로봇 자체 안전" 이벤트(충돌/전복)로 기록할 수 있다 — real_hal.py의 read_line_sensors/이동 로직에 헤딩 보정을 추가할 자리다.

온디맨드 피킹 안내 (사용자가 특정 물품을 찾을 때)

정기 실사와 별개로, 사용자가 웹에서 특정 물품을 대여 신청하면 로봇이 같은 2단계 인식 로직으로 그 자리에서 확인해준다. 그리퍼가 없어 직접 집어주지는 못하므로, 로봇의 역할은 "어떤 개체를 가져가야 하는지 확정해서 안내"하는 데 그친다.

09 아두이노 게이트

스마트 대여소 게이트

게이트는 물리적으로 두 개의 독립된 장치로 구성된다 — 아두이노(RFID+릴레이+LCD+부저)와 XIAO ESP32S3 Sense(카메라+WiFi). 둘을 직접 유선으로 연결하지 않고, 각자 웹 API를 호출하게 한 뒤 웹이 시간 기준으로 두 이벤트를 묶어서 대여/반납을 확정한다. 물품 QR을 스캔한 시점에 그 물품의 현재 상태가 "대여가능"이면 대여로, "대여중"이면 반납으로 자동 분기한다.

왜 둘을 직접 연결하지 않나 아두이노 우노 호환보드는 5V 로직, XIAO ESP32S3는 3.3V 로직이다. UART로 직접 연결하면 레벨시프터 없이는 XIAO가 손상될 수 있다. 대신 아두이노는 기존처럼 USB 시리얼로 PC/Pi에 연결하고, XIAO는 자체 WiFi로 웹 API를 직접 호출하는 완전히 분리된 두 클라이언트로 둔다 — 배선 리스크 없이 더 단순해진다.

대여 흐름

"누가"(RFID, 아두이노 경유)와 "무엇을"(물품 QR, XIAO 경유)이 몇 초 이내에 함께 들어와야 하나의 대여 요청으로 묶인다.

반납 흐름

반납은 원래 빌린 사람이 아니어도 할 수 있어야 하므로, RFID는 "반납자 기록용"으로만 선택적으로 쓰고 물품 QR만으로도 반납이 성립하게 한다.

HC-SR04 대기모드 (스트레치) 게이트에 별도 초음파센서(HC-SR04)를 달아 사람이 다가올 때만 카메라·RFID를 활성화한다. 필수는 아니지만 시간이 남으면 붙이기 쉬운 개선이다.
반납 후 반납된 물건이 정위치에 다시 놓이는지는 게이트가 보장하지 않는다. 다음 실사 순찰에서 Raspbot이 QR로 위치를 확인해 불일치가 있으면 리포트에 잡는다 — 08번 실사 로직을 그대로 재사용한다.
10 Safety 모듈 (LabFlow 통합)

ROS2·Isaac Sim 대신, 이미 만든 것으로

팀 내부 기획서(LabFlow v1.2, 14장 "실행 현실화 개정안")와 합의된 최종 결정을 여기 반영한다: ROS2와 Isaac Sim은 장기 비전으로만 남기고, v1은 지금 이미 동작하는 robot-sim(pygame)과 HAL 패턴을 정식 SIM/REAL 교체 인터페이스로 채택한다. 새 테이블도 LabFlow가 제안한 25개 이상의 엔터티가 아니라, 축소된 SafetyEvent + ActionLog 두 개만 추가한다 — 이미 구현하고 실제로 폐쇄루프까지 검증했다.

SR-05/06/07은 새로 안 만든다 위치 불일치·재고/대여 상태 불일치·점검 누락은 이미 AuditMismatch가 처리한다. 여기서 다루는 건 로봇이 실시간으로 감지하는 물리적 이상(SR-01 통로장애물, SR-08 충돌위험, SR-03 사람감지)뿐이다.

stateDiagram-v2

로봇 감지는 항상 NEEDS_REVIEW로 시작한다 — AI/센서 판정은 오탐 가능성이 있으므로 "자동 확정"하지 않는다. CLOSED/FALSE_POSITIVE 상태는 사용자가 임의로 삭제하거나 되돌릴 수 없고, 모든 전이가 ActionLog에 남는다.

Robot Console 원칙

  • 웹에서 원격으로 E-stop을 해제하는 기능은 제공하지 않는다 — 현장 확인 후 로봇 쪽에서 수동으로만 재가동한다.
  • 로봇 로컬 제어가 정지 판단을 우선한다. 통신이 끊겨도 로봇 스스로 멈출 수 있어야 한다.

12 실물 목업 가이드

집에서 준비할 것

대부분의 로직은 가상 연구실에서 이미 검증됐으므로, 실물 목업은 "현실에서도 똑같이 동작하는가"만 확인하는 최소 규모로 줄인다. 대규모 선반 배치를 집에 마련할 필요가 없다.

  • 재고 물품: 방에 있는 책·부품·소품 10~20개에 QR 스티커 부착(직접 발급한 QR 이미지 인쇄)
  • 선반 목업: 책장 한 단 또는 박스로 2~3개 구역 구성, 각 구역 앞에 정지선 테이프
  • 라인트랙: 검은 절연테이프로 바닥에 경로 부착 (Raspbot 라인트래킹 센서용)
  • RFID 카드: 본인 및 지인 2~3명의 카드/태그를 등록해 실제 사용자처럼 시연
  • 게이트 목업: 작은 상자 + 서보/솔레노이드 잠금장치로 "보관함" 표현, 실제 문이 아니어도 됨
  • 게이트 카메라: XIAO ESP32S3 Sense 1개 (자체 WiFi로 QR 이벤트를 웹 API에 직접 전송, PC 브리지 불필요)
  • 게이트 대기감지(선택): HC-SR04 초음파센서로 사람 접근 시에만 활성화
  • Raspbot 헤딩 보정: MPU6050(IMU)을 I2C로 연결해 실제 회전각 측정, 충돌/전복 감지

14 리스크 & 고려사항

미리 점검할 것

범위 관리 1인 개발이므로 1단계(웹 MVP)를 먼저 완전히 끝내고, 로봇/아두이노는 순차적으로 붙인다. 세 가지를 동시에 진행하면 어느 것도 완성도가 나오지 않는다.
네트워크 Raspbot과 웹 서버가 같은 네트워크(또는 터널)에 있어야 한다. 집 와이파이 환경에서 고정 IP/포트포워딩 또는 ngrok류 터널을 미리 테스트한다.
인식 정확도 조명/각도에 따라 QR·얼굴 인식률이 떨어질 수 있다. 정지 후 스캔(정지 상태에서만 인식)으로 오탐을 줄인다.
Sim-to-Real Gap 가상 연구실에서 완벽히 동작한 로직이 실물에서 그대로 통한다는 보장은 없다(조명 노이즈, 모터 오차, 마찰). 3단계(실제 Raspbot 검증)를 절대 생략하지 말고, 실측에서 얻은 보정치를 다시 Sim Engine에 반영해 가상환경의 신뢰도를 계속 끌어올린다.
