1. 과제 개요

LabKeeper는 실습실·랩의 물품 대여와 재고를 관리하는 웹 서비스다. 이 웹은 로봇이 없어도 등록·검색·대여·반납·실사·통계 기능만으로 실제 실습실 운영에 쓸 수 있도록 독립적으로 완성하는 것을 원칙으로 한다.

여기에 라즈베리파이 기반 로봇카(Raspbot)와 아두이노를 결합해, 로봇이 재고를 자동으로 실사하고 대여소 게이트가 대여·반납을 물리적으로 확인하는 Physical AI 확장 기능을 더한다. 즉 "로봇카를 위한 웹"이 아니라 "쓸 만한 웹에 로봇을 연결해 현실까지 확장하는 프로젝트"를 지향한다.

2. 추진 배경 및 필요성

실습실·메이커스페이스에서는 아래와 같은 문제가 반복적으로 발생한다.

  • 위치 파악의 어려움 — 물품이 어느 선반에 있는지 정확히 아는 사람이 없어 매번 찾아다녀야 한다.
  • 대여 기록의 부재 — 누가 무엇을 언제 빌렸는지 종이로 적거나 아예 기록하지 않아, 분실·연체 추적이 안 된다.
  • 재고 실사의 공백 — 실물과 장부가 맞는지는 보통 연 1회 전수조사 때만 확인해, 그 사이 발생한 불일치를 놓친다.

이 문제는 대부분 수기 관리·낮은 확인 빈도에서 비롯된다. 웹으로 기록을 표준화하고, 로봇으로 확인 빈도와 정확도를 높이면 실질적으로 해결 가능하다.

4.2 로봇 확장 기능

Raspbot에는 그리퍼가 없어 물건을 직접 옮기지 못한다. 대신 이동 + 인식으로 웹의 데이터를 자동으로 확인·갱신하는 역할을 맡는다. 개체를 정확히 식별해야 하는 모든 순간에는 QR을, 넓은 구역을 빠르게 훑는 순간에는 객체인식을 쓰는 2단계 인식 전략을 전 기능에 공통으로 적용한다.

기능트리거인식 방식1주차 범위
자동 재고 실사 순찰관리자가 웹에서 실사 시작1차 객체인식(구역별 개수 확인) → 2차 QR(불일치 구역 정밀 확인)구현 (축소판)
온디맨드 피킹 안내사용자가 특정 물품 대여 신청1차 객체인식(카테고리 위치 확인) → 2차 QR(대여 가능한 개체 확정 및 예약)이후 단계
대여소 게이트 확인사용자가 물품을 들고 게이트 태그RFID(사용자) + QR(물품) 동시 확인 → 대여/반납 확정이후 단계 (웹 수동 처리로 대체)

4.3 시스템 구성 개요

웹 서비스가 유일한 데이터 원천이며, 가상 로봇과 실제 Raspbot은 동일한 코드(인식·판단 로직)로 동작하고 센서·구동 인터페이스만 교체된다. 상세 아키텍처, 데이터 모델, API 명세는 별도 기술 설계 문서에서 다룬다.

5. 추진 방법

5.1 개발 전략 — 가상 검증 후 실물 이식 (장기 전략)

실제 랩 공간과 다수의 로봇을 확보하기 어려우므로, 컴퓨터 안에 가상 연구실(디지털 트윈)을 만들어 로직을 먼저 개발·반복 검증하고, 완성된 로직만 실제 Raspbot에 옮겨 소규모 목업에서 최종 확인하는 것이 장기적인 개발 전략이다.

이번 스프린트 예외 제출기한이 1주라 가상 연구실을 구축할 시간이 없다. 이번 스프린트는 위 전략을 건너뛰고 실제 Raspbot으로 바로 개발하며, 디지털 트윈 전략은 8장의 이후 단계부터 본격적으로 적용한다.
핵심 원칙 웹은 항상 완전히 동작해야 한다. 가상환경과 실물 로봇은 웹의 데이터를 자동으로 확인·갱신하는 보조 수단이며, 둘 다 없어도 웹은 수동 입력으로 100% 동작해야 한다.

5.2 기술 스택

백엔드 FastAPI + PostgreSQL, 프론트엔드 React, 로봇/시뮬레이터 클라이언트는 Python(OpenCV) 공통 코드로 작성한다.

9. 기대효과 및 활용방안

  • 운영 효율화 — 실습실 물품의 위치·대여 상태·재고 정확도를 상시 파악할 수 있다.
  • 확인 빈도 향상 — 연 1회 수준이던 재고 실사를 로봇이 상시 순찰로 대체해 불일치를 조기에 발견한다.
  • 재현 가능한 개발 방법론 — 가상 연구실(디지털 트윈)로 검증 후 실물에 이식하는 구조는 로봇/공간 자원이 부족한 다른 프로젝트에도 그대로 적용 가능하다.
  • 확장성 — 동일한 웹·로봇 구조를 도서관, 소규모 창고 등 유사한 대여·재고 도메인에도 이식할 수 있다.
